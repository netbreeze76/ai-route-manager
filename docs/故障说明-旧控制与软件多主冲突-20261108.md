# AI Route Manager 旧控制与软件多主冲突故障说明

日期：2026-11-08（Asia/Shanghai）
修复版本：1.0.1

## 结论

本次故障不是某一条线路单独失效，而是同一台电脑上同时保留了三套会写入代理状态的控制面：

1. 最早的 PowerShell「VPN 分流控制台」与计划任务；
2. 后来形成的 AI Route Manager 软件及其托管引擎；
3. 为 Steam Cloud 临时加入的软件外 Python 稳定入口与启动项。

三套控制面会分别改写 WinINet、用户 WinHTTP、环境变量、计划任务和本地监听端口。旧控制台执行“检查并自动修复”时，只认识旧任务和 FlClash 7890；它发现旧任务已由迁移流程停用后，把系统代理切回 7890，并把“任务已禁用”误报成恢复失败。AI Route Manager 随后又把 WinINet 抢回 27898，造成不同应用看到不同出口、状态来回变化。

## 项目演进关系

### 第一阶段：脚本控制

最初由 `Control-VPN.ps1`、`Repair-VPN.ps1`、`Watchdog-VPN.ps1` 和 `DynamicProxyManager*` 计划任务负责本机分流。端口体系为 17898/17899，稳定入口为 17901，FlClash 7890 是热备。

### 第二阶段：形成软件

AI Route Manager 把连接配置、预演、迁移、托管、自愈、推荐中心和设备能力集中到图形软件。软件使用独立的托管核心 27898/27899，并通过 `AI Route Manager Supervisor` 恢复运行。迁移完成后，旧任务应只作为可回滚记录，不能继续作为日常控制入口。

### 第三阶段：软件外补丁

Steam Cloud 暴露了一个遗漏：软件只轮换 27898/27899，没有真正提供自己的 17901 稳定消费入口；部分程序仍读取 WinHTTP 或环境变量。临时修复用 Python 在软件外补了一层 17901，并新增启动项。该修复恢复了 Steam Cloud，但重新引入了第二个控制者。

### 本次触发

用户再次运行桌面旧版「VPN 分流控制台」。旧控制台不了解软件的 27898/27899、软件监督器和迁移提交状态，于是按旧规则切换到 FlClash 7890，并尝试启动已经禁用的旧任务，出现截图中的失败。

## 根因

### 直接根因

- 旧桌面入口没有在迁移完成后退役；
- `DynamicProxyManager-Watchdog` 仍为启用状态；
- AI Route Manager 1.0.0 把 `DPM_FRONTEND_PORT` 设为 `0`，稳定入口并不属于软件；
- Steam 修复把 17901 放在独立 Python 进程和独立 Run 启动项中；
- WinINet、WinHTTP 和环境变量没有共同的唯一所有者。

### 流程根因

此前把“旧控制可回滚”理解成了“旧控制仍可继续日常运行”。回滚材料与生产控制入口没有隔离。后续故障修复又只补齐了 Steam 的消费入口，没有先把补丁并回软件，导致控制权继续分裂。

## 1.0.1 修复

1. AI Route Manager 内置原生 TCP 稳定入口 `127.0.0.1:17901`；每个新连接按托管状态转发到当前 27898 或 27899，核心轮换不再要求消费者改端口。
2. 软件启动的托管引擎统一使用 `DPM_FRONTEND_PORT=17901`，WinINet 由引擎保持在软件稳定入口。
3. 软件监督器同步用户级 `HTTP_PROXY`、`HTTPS_PROXY` 和 WinHTTP advanced proxy 到 17901；旧入口再次改写后最多 30 秒恢复。
4. 独立 Python 稳定入口和 `AIRouteStableFrontdoor` 启动项在安装 1.0.1 后退役。
5. `DynamicProxyManager` 与 `DynamicProxyManager-Watchdog` 都保持禁用。
6. 桌面的旧「一键恢复」入口改成只启动 AI Route Manager，不再修改代理、任务或进程。
7. 旧源码和任务 XML只保留在可验证回滚包中，不再充当生产入口。

## 全局同因回查

- 检查所有桌面脚本、Run 启动项和计划任务，寻找会写入 7890、17901、17898/17899、27898/27899 的入口；
- 检查 WinINet、WinHTTP、HTTP_PROXY、HTTPS_PROXY 是否指向同一软件入口；
- 检查 17901 的进程所有者必须是 AI Route Manager，而不是 Python、旧 Manager 或脚本看守；
- 检查 GUI、无界面监督器、托管引擎和核心均为单实例；
- 验证 Steam Cloud、ChatGPT/Claude/Google、Telegram 专用 17896 和国内直连互不串线；
- 验证软件核心轮换后 17901 地址不变、现有连接自然排空、新连接进入新核心。

## 以后遵循的原则

1. 生产状态只能有一个写入者；软件版本是最终权威。
2. 回滚包可以保留原控制，但桌面日常入口必须退役或转发到软件。
3. 临时修复验证通过后必须并回软件，再删除外置看守和重复启动项。
4. 任何迁移都同时盘点 WinINet、WinHTTP、环境变量、计划任务、Run 项、端口所有者和桌面入口。
5. “当前能访问”不等于迁移完成；还要验证重启、自愈、轮换、回滚和旧入口隔离。

## 本次修复中发现并彻底改正的同因错误

1. 第一版原生稳定入口把监听器设为非阻塞，却没有把 `accept` 得到的客户端套接字恢复为阻塞模式。HTTP CONNECT 能返回 200，但 TLS 数据转发会在 `WouldBlock` 后提前结束。现已在每个已接受连接上显式执行 `set_nonblocking(false)`；全局回查确认项目中没有第二个同类非阻塞监听转发器。
2. 清理外置 Python 入口时，最初按命令行文本匹配进程，执行清理的 PowerShell 自身命令行也含有同一文本，因此误匹配了当前清理进程。后续所有生产清理均改用已经核实的 PID、可执行文件路径和监听端口所有者，不再用宽泛命令行包含关系结束进程。
3. 验证脚本第一次交给 Windows PowerShell 5.1 时，UTF-8 无 BOM 的中文路径和无 BOM JSON 被按本地代码页读取。脚本现使用 UTF-8 BOM，并对 JSON/源码显式指定 `-Encoding UTF8`；同类脚本已一并检查。
4. 调试构建在 GNU 工具链下触发 DLL 导出符号上限。产品验收统一回到项目既定的 `scripts/test-rust-gnu.ps1` 和 release 构建链，避免把调试链接器限制误判成产品逻辑失败。
